# 工程模块拆分原则

日期：2026-06-15

本文档记录后续实现第一章、怪物、奖励、商店、善恶值卡牌时的模块边界。

目标是避免所有规则继续堆进 `combat_scene.gd`，让每个功能只负责自己的职责，便于后续扩展和测试。

这里说的“拆分”主要指代码职责拆分，不是要求每个功能都做成独立预制体。

一个角色预制体可以包含立绘、血条、状态、意图等多个显示节点。不同功能的显示可以最终合并在同一个预制体中，但背后的代码应保持职责清晰。

## 当前状态

当前 demo 中，`scripts/ui/combat_scene.gd` 同时承担了多个职责：

- 战斗初始化。
- 回合流程。
- 抽牌、弃牌、出牌和牌堆移动。
- 卡牌效果解析。
- 资源、伤害、状态和变身结算。
- 敌人意图选择。
- UI 刷新。
- 战斗日志。

这在最小 demo 阶段可以接受，但不适合作为完整章节和完整牌池的长期结构。

后续新增功能时，应逐步把这些职责拆出去，让 `combat_scene.gd` 变成 UI 场景入口和协调器，而不是规则系统本身。

## 已落地模块

当前已经从 `combat_scene.gd` 拆出的模块：

- `scripts/combat/card_zone_manager.gd`：负责抽牌、洗牌、弃牌、出牌后去向和变身卡持有区。
- `scripts/combat/effect_resolver.gd`：负责读取卡牌效果列表并按效果类型分发。
- `scripts/combat/resource_system.gd`：负责生命、魔力、魔力防御、护盾、发情、敏感和堕落等资源变化。
- `scripts/combat/damage_system.gd`：负责当前伤害效果的护盾、魔力防御和生命扣除。
- `scripts/combat/status_system.gd`：仅负责稳定的状态添加、移除、叠层和文本展示。
- `scripts/combat/target_resolver.gd`：负责目标类型解析和目标合法性判断。
- `scripts/combat/combat_controller.gd`：负责战斗阶段、回合数和胜负状态。
- `scripts/combat/unit_state_factory.gd`：负责把角色/敌人表格行转换成战斗运行时单位数据。
- `scripts/enemy_ai/enemy_ai_controller.gd`：负责敌人 AI 调用入口和兜底行动选择。

`combat_scene.gd` 当前仍保留 UI 输入、UI 刷新、战斗日志、异步敌人回合播放、临时变身解除检查，以及少量模块之间的协调代码。

## 总体原则

- UI 只显示状态和发出玩家操作，不直接写战斗规则。
- 战斗规则不依赖具体 UI 节点。
- 预制体可以组合多个显示功能，代码模块不要因此互相承担规则职责。
- 效果系统不硬编码具体卡牌 ID。
- 敌人 AI 不直接修改战斗状态，只返回要执行的行动。
- 章节、奖励、商店、休息点不直接操作手牌、弃牌堆或具体 UI 节点。
- 数据表负责声明数据，规则系统负责解释数据，UI 负责展示结果。
- 新功能优先新增模块或扩展已有模块，不把逻辑继续塞进 `combat_scene.gd`。

## 推荐模块边界

### 数据层

负责读取和查询表格数据。

现有：

```text
scripts/core/table_loader.gd
scripts/data/game_database.gd
```

职责：

- 加载 CSV。
- 按 ID 查询卡牌、效果、敌人、关卡、奖励池等配置。
- 不执行战斗规则。
- 不直接修改运行时状态。
- 不依赖 UI。

后续可以增加更具体的查询方法，但不要把战斗结算写进数据层。

### 战斗状态层

负责保存一场战斗的运行时状态。

建议后续新增：

```text
scripts/combat/combat_state.gd
```

职责：

- 玩家状态。
- 敌人状态列表。
- 当前回合、阶段、胜负状态。
- 抽牌堆、手牌、弃牌堆、除外堆、能力区、状态持有区。
- 当前变身、善恶值来源、临时火力、临时防御、反射等运行时数据。

战斗状态层只存数据，不主动执行复杂规则。

### 牌堆与卡牌生命周期

负责所有卡牌移动和牌区规则。

现有：

```text
scripts/combat/card_zone_manager.gd
```

职责：

- 构建初始牌组。
- 抽牌。
- 洗弃牌堆。
- 手牌上限处理。
- 回合结束弃牌。
- 打出后进入弃牌堆、除外堆、状态持有区、能力区或消失。
- 变身卡解除后回到弃牌堆。
- 能力牌打出后离开普通牌堆并进入能力区或隐藏生效区。

其他系统不应该直接 `append` 或 `pop_front` 各种牌堆，而应该通过这个模块。

### 效果系统

负责解释和执行卡牌效果。

现有：

```text
scripts/combat/effect_resolver.gd
```

职责：

- 读取卡牌的效果列表。
- 按效果类型分发。
- 处理资源变化、伤害、护盾、抽牌、弃牌、善恶值、状态、变身等效果。
- 处理善恶双态分支。
- 返回结算日志和触发事件。

约束：

- 不直接访问 UI 节点。
- 不硬编码具体卡牌 ID。
- 不负责选择敌人行动。
- 不负责章节奖励。

### 资源与状态系统

负责角色身上的数值和状态规则。

现有：

```text
scripts/combat/resource_system.gd
scripts/combat/status_system.gd
scripts/combat/transform_system.gd
scripts/combat/alignment_system.gd
scripts/combat/character_metric_system.gd
```

职责：

- 生命、魔力、魔力上限、魔力防御、魔力护盾。
- 善恶值、善恶来源、进入善/进入恶、向善/向恶变化。
- 魔法少女状态数值，例如发情值、敏感值、堕落值、恐惧值、羞耻值、依赖值。
- 状态数值的上限、下限、持续范围、来源记录和查询接口。
- 火力、临时火力、防御、临时防御、反射、临时反射。
- 状态添加、移除、层数、到期。
- 多个变身并存、变身解除、变身封锁、限时变身、变身卡归属。

这些系统应提供清晰方法给效果系统调用，而不是让效果系统到处直接改字典字段。

当前状态与变身的具体设计还会随着后续卡牌和怪物继续变化，因此拆分时先抽稳定的通用能力：

- 状态添加。
- 状态叠层。
- 状态移除。
- 状态文本展示。

暂时不要过早把变身、多变身、限时变身、状态触发时机和持续时间写成固定框架。等卡牌与怪物设计更稳定后，再扩展 `transform_system.gd` 和完整 `status_system.gd`。

### 伤害系统

负责统一伤害结算。

现有：

```text
scripts/combat/damage_system.gd
```

职责：

- 普通造成伤害效果。
- 魔力护盾、魔力防御、生命值扣除。
- 火力和临时火力加成。
- 易伤等受到伤害修正。
- 反射伤害。
- 伤害事件广播。

规则边界：

- 火力只加成普通造成伤害效果。
- 反射不走普通造成伤害效果，因此不吃火力。
- 易伤修改受到的伤害，因此反射会吃易伤。
- 伤害系统负责避免递归伤害或转化效果无限循环。

### 目标选择系统

负责卡牌和效果的目标合法性。

现有：

```text
scripts/combat/target_resolver.gd
```

职责：

- 判断卡牌能否选中目标。
- 根据 target 类型返回实际目标。
- 支持单体、群体、自身、随机敌人等后续扩展。

UI 可以询问目标是否合法，但不应该自己实现完整目标规则。

鼠标点中了哪个预制体或 UI 节点，属于 UI 输入层，可以留在 `combat_scene.gd` 或对应 UI 控件中。

目标规则本身，例如“自身牌只能选自己”“单敌牌只能选敌方”“敌人使用单敌牌时目标是玩家”，属于 `target_resolver.gd`。

### 敌人 AI

负责根据战斗状态选择敌人行动。

现有：

```text
scripts/enemy_ai/corrupted_student_ai.gd
```

现有：

```text
scripts/enemy_ai/enemy_ai_controller.gd
scripts/enemy_ai/corrupted_student_ai.gd
```

后续建议：

```text
scripts/enemy_ai/enemy_ai_base.gd
scripts/enemy_ai/*.gd
```

职责：

- 读取当前战斗上下文。
- 返回下一张敌人行动卡 ID 或行动 ID。
- 不直接造成伤害。
- 不直接修改玩家或敌人状态。
- 不直接刷新 UI。

每个怪物可以有自己的 AI，也可以使用表驱动 AI。

### 战斗流程控制

负责一场战斗的阶段推进。

现有：

```text
scripts/combat/combat_controller.gd
```

职责：

- 开始战斗。
- 玩家回合开始。
- 玩家打牌。
- 玩家回合结束。
- 敌人回合。
- 胜负检查。
- 战斗结束事件。

它可以调用效果系统、牌堆系统、敌人 AI 和状态系统，但不直接承载所有细节。

### 章节与地图流程

负责第一章节点推进。

建议后续新增：

```text
scripts/run/run_state.gd
scripts/run/chapter_controller.gd
scripts/run/choice_condition_resolver.gd
```

职责：

- 当前章节。
- 当前节点。
- 玩家当前生命、金币、牌组、永久善恶值。
- 玩家局内或长期状态数值。
- 普通战斗、精英战斗、Boss、商店、休息点的节点切换。
- 事件选项的显示条件、禁用条件、结果分支和代价变化。
- 章节胜利和失败。

章节流程不应该知道战斗内部如何抽牌或如何结算伤害。

### 奖励系统

负责战斗结束后的奖励。

建议后续新增：

```text
scripts/reward/reward_generator.gd
scripts/reward/reward_controller.gd
```

职责：

- 根据战斗类型生成奖励。
- 卡牌三选一。
- 金币奖励。
- 永久善恶变化。
- 奖励池和稀有度权重。
- 玩家选择奖励后写回局内状态。

奖励系统不负责战斗结算，也不直接刷新战斗 UI。

### 商店系统

当前版本只卖卡牌。

建议后续新增：

```text
scripts/shop/shop_controller.gd
```

职责：

- 生成商店卡牌列表。
- 标价。
- 检查金币。
- 购买后把卡加入牌组。
- 买过的商品移除。

商店不直接改战斗中的手牌和牌堆，只改局内牌组。

### 休息点系统

建议后续新增：

```text
scripts/rest/rest_controller.gd
```

职责：

- 回复生命。
- 后续如果需要，再加入升级卡牌。

休息点不处理战斗逻辑。

### UI 层

负责展示和输入。

现有：

```text
scripts/ui/combat_scene.gd
scripts/ui/card_view.gd
scripts/ui/unit_view.gd
scripts/ui/target_arrow_layer.gd
```

后续职责边界：

- `combat_scene.gd` 只负责连接 UI 和 `CombatController`。
- `card_view.gd` 只显示卡牌和发出拖拽/点击信号。
- `unit_view.gd` 只显示单位生命、护盾、状态和意图。
- UI 不直接结算效果。
- UI 不直接决定奖励内容。
- UI 不直接选择敌人行动。

## 后续拆分顺序

为了不一次性大拆，建议按以下顺序逐步拆：

1. 已完成：先抽出 `card_zone_manager.gd`，把抽牌、弃牌、洗牌、出牌后去向从 `combat_scene.gd` 移出去。
2. 已完成：抽出 `effect_resolver.gd`，把卡牌效果解析和效果分发移出去。
3. 已完成：抽出 `damage_system.gd` 和 `resource_system.gd`，统一伤害、护盾、魔力、生命值结算。
4. 部分完成：抽出 `status_system.gd` 的稳定状态能力；`alignment_system.gd` 和 `transform_system.gd` 等善恶值、多变身规则等设计稳定后再做。
5. 已完成：抽出 `target_resolver.gd` 和 `enemy_ai_controller.gd`，让目标规则与敌人行动选择离开 UI 场景。
6. 已完成：抽出 `combat_controller.gd` 和 `unit_state_factory.gd`，把阶段、回合、胜负状态与单位初始数据创建移出去。
7. 待做：继续收敛 `combat_scene.gd` 中的异步敌人回合、战斗结束事件、变身解除检查和 UI 协调边界。
8. 待做：再实现章节、奖励、商店和休息点。
9. 待做：最后批量录入并实现 48 张卡牌。

## 不建议的做法

- 不要在 `combat_scene.gd` 中继续增加大量卡牌特判。
- 不要用卡牌 ID 写死效果逻辑。
- 不要让敌人 AI 直接改玩家生命或状态。
- 不要让奖励界面直接操作战斗中的手牌或弃牌堆。
- 不要让 UI 节点成为规则系统的依赖。
- 不要让章节流程知道具体某张卡怎么结算。

## 近期执行口径

在开始实现怪物和章节前，先把后续新增代码尽量放进对应模块。

如果某个功能暂时必须留在 `combat_scene.gd`，需要满足：

- 逻辑足够小。
- 不包含具体卡牌 ID 特判。
- 后续能明确迁移到某个模块。
- 不阻塞当前 demo 运行。
